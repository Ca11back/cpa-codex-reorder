# codex-reorder

面向 [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)（下文简称 CPA）的 Codex 多账号调度插件。

在 CPA 挂载多个 Codex 账号（OAuth / PAT 授权文件）的场景下，插件接管 Codex 路由决策，解决以下问题：

- **会话粘性**：同一会话固定路由至同一账号，避免频繁切换导致提示词缓存失效。
- **负载均衡**：新会话自动分散到当前活跃会话最少的账号，避免单号同时承载过多会话。
- **额度感知**：结合周额度重置时间、剩余比例与套餐体量计算紧迫度，优先消耗临近过期且余量充足的账号，减少额度浪费。
- **可观测与运维**：内置 Web 面板（查看额度与绑定、实时预览并修改排序规则）、可选自动开窗、手动额度查询，以及独立的生图路由。

> 配置文件中的 `codex-api-key` 默认交由 CPA 原生逻辑处理，不纳入本插件调度，原因见[账号与 API Key](#账号与-api-key)。

## 快速开始

### 环境要求

- CPA `v8.0.61` 及以上（插件 C ABI 1，已在 `v8.0.61`–`v8.0.75` 验证）
- Linux，Go `1.26+`，以及 cgo 所需的 `gcc`

### 编译

```bash
make build
```

构建产物位于 `dist/codex-reorder.so`。`Makefile` 默认锁定基础指令集（amd64 使用 `GOAMD64=v1`，arm64 使用 `GOARM64=v8.0`），确保在较老的 CPU 或虚拟机上也能正常加载。

### 部署与启用

1. **停用其他 Codex 调度插件。** CPA 同一时间仅允许一个调度插件生效。若此前安装过类似插件（如 `codex-quota-scheduler`），请将其 `enabled` 设为 `false` 或移除对应的 `.so`。部分调度插件即使不负责调度，仍会监听用量或拦截请求，务必彻底停用。
2. **放置插件文件。** 将 `dist/codex-reorder.so` 复制到 CPA 插件目录（CPA 优先扫描 `plugins/linux/amd64/`，其次为 `plugins/`）。插件 ID 由文件名决定，`codex-reorder.so` 与 `codex-reorder-v0.6.6.so` 均识别为 `codex-reorder`。`config.yaml` 中未声明其配置时不会加载，因此可以先放文件、后启用。
3. **合并配置。** 参考 [config.example.yaml](config.example.yaml)，将 `plugins.configs.codex-reorder` 配置段写入 CPA 的 `config.yaml`。CPA 会自动热重载，无需重启。
4. **验证加载。** CPA 日志应出现 `codex-reorder 0.6.6 configured: order=...`；如有配置告警，会紧随一条 `codex-reorder config:` 输出。
5. **访问面板**：`https://<CPA地址>/v0/resource/plugins/codex-reorder/dashboard`，输入 CPA 管理密钥即可查看实时状态。

> **切换提示**
> - 插件启用瞬间，正在进行的会话会各被重新分配一次（插件无法读取 CPA 内存中的原有粘性表），建议在低峰期上线。
> - 若从 CPA 原生粘性迁移，请将 `session_ttl` 设为与原 `routing.session-affinity-ttl` 一致的值（如 `1h`）。插件接管后，CPA 原生粘性对 Codex 不再生效，但对其他 provider 仍然有效，建议保持开启。
> - 将 `enabled` 设为 `false` 即可卸载插件，即时退回 CPA 内置调度。

## 调度机制

### 会话粘性与故障切换

会话首次到达时被绑定至目标账号，后续请求持续路由到该账号，直至闲置时间超过 `session_ttl`（默认 `30m`）。

仅当原账号**本次**无法服务时，会话才会迁移：请求出错触发 CPA 换号重试、账号处于冷却、被禁用、不支持目标模型，或已知周额度耗尽。**迁移后永久绑定至新账号，原账号恢复后不回切**，与 CPA 默认的 `session-affinity-rebind-on: any` 一致。

> 不回切的原因：每次换号都伴随一次失败重试，且新账号上的缓存为空。实测"临时转走、恢复后转回"的策略会让一个会话在半小时内于 4 个账号之间跳转 7 次，不如一次迁移到底。

### 新会话排序规则

新会话到达时，插件按 `order` 定义的字段顺序对所有可用账号进行链式比较：前一项分出胜负即确定排名，打平时再比较下一项，排名第一的账号接收该会话。

| 规则字段 | 排序逻辑 | 说明 |
|---|---|---|
| `priority` | CPA 凭据优先级高者优先 | 所有账号优先级相同时不生效 |
| `sessions` | 当前活跃会话数少者优先 | 分散并发压力 |
| `unopened_first` | 周额度窗口尚未开始计时者优先 | 尽早启动 7 天计时，避免周期空转（见[自动开窗](#自动开窗)） |
| `unopened_last` | 周额度窗口尚未开始计时者靠后 | 与上一条相反，适合有意延后开窗的场景 |
| `urgency` | 紧迫时间最早者优先 | 综合重置时间与剩余额度，见下文 |
| `reset` | 周额度重置时间最早者优先 | 仅看重置时间，不考虑剩余比例 |
| `remaining` | 剩余周额度（剩余百分比 × 套餐倍数）多者优先 | 优先消耗余量最大的账号 |

默认顺序为 `priority, sessions, unopened_first, urgency`，含义依次为：

1. 先遵守 CPA 优先级；
2. 再在同级账号间均衡会话数；
3. 同样空闲时，优先启用尚未开始计时的账号（闲置不用就会少拿一个周期的额度）；
4. 最后按额度紧迫度分配。

#### 紧迫时间（`urgency`）

```text
紧迫时间 = 周额度重置时间 − 剩余百分比 × 套餐倍数 × urgency_minutes_per_percent
```

单看重置时间并不够。例如账号 A 10 小时后重置、仅剩 5%，账号 B 晚 10 分钟重置、却剩 90%：B 有大量额度需要尽快消耗，显然更"紧迫"。按默认系数（每 1% 折算 1 分钟）计算，A 的紧迫时间为 9 小时 55 分，B 为 8 小时 40 分，B 优先。而若 A 明天重置、B 后天重置，两者相距过远，剩余额度的折算追不上时间差，A 依然优先。

换言之：重置时间相近时，剩余越多越优先；重置时间相距较远时，临期账号优先；两者之间平滑过渡。将 `urgency_minutes_per_percent` 设为 `0` 即退化为纯 `reset` 排序。

### 固定约束

- **耗尽账号垫底**：已知周额度耗尽的账号（只会返回 429）永远排在最后，此规则不可修改。
- **最终兜底**：所有 `order` 字段均打平时，按最久未分配时间、再按账号 ID 决出先后。
- **连续值规则**：`urgency`、`reset`、`remaining` 为连续数值，几乎不会打平，排在它们之后的规则通常不会生效。
- **并发集中提醒**：`order` 中未包含 `sessions` 时，新会话会集中到少数账号，面板与日志会给出提醒。
- **候选过滤**：被禁用、处于冷却、不支持目标模型的账号，CPA 不会交给插件，自然不参与排序。
- **冷启动防扎堆**：刚分配了新会话、尚未获得额度数据的账号，暂按"窗口已开始计时、剩余 100%"参与排序，防止紧接着的新会话继续涌向同一账号。
- **5 小时窗口**：不参与排序，触达上限时由 CPA 自身的冷却机制处理。

### 账号与 API Key

配置文件中的 `codex-api-key` 没有周额度和 5 小时窗口，上述规则对其没有意义。更严重的是，没有额度数据的 Key 会被视为"尚未开始计时"，在默认规则下排到最前，把新会话引向按量计费的 Key。因此默认行为是：

- 候选集同时包含账号与 Key：仅在账号中挑选；
- 仅剩 Key 可用：整次调度交还 CPA；
- 存在优先级高于全部账号的 Key：同样交还 CPA（CPA 自身会优先使用它）。

如需由插件一并调度 Key，设置 `manage_api_keys: true`。

### 特殊请求

- **无会话 ID 的请求**：照常按 `order` 选号，但不建立会话绑定。经 new-api 等中转的 Codex 请求通常携带 `prompt_cache_key`，CPA 会据此生成会话 ID。
- **单候选锁定（`held`）**：例如在 Codex WebSocket 长连接中，CPA 将整条连接固定在原账号上。此时即便原账号额度已满也无其他账号可选，插件维持原路由、不修改绑定；待上游返回 429、连接断开、客户端重连后，下一次请求再正常换号。
- **带前缀模型（`pinned`）**：请求 `<账号前缀>/<模型>` 时，CPA 仅给出前缀匹配的账号，插件直接使用，但不覆盖该会话原有绑定，后续不带前缀的请求仍回到原账号。效果与 CPA 原生"按会话 + 模型分别绑定"一致。
- **生图请求**：走独立通道，见[生图请求路由](#生图请求路由)。
- **非 Codex 或混合 provider 请求**：插件不处理，直接交还 CPA。

## 配置参考

以下配置均位于 CPA `config.yaml` 的 `plugins.configs.codex-reorder` 节点下。排序与开窗相关参数也可直接在 Web 面板中修改。

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `order` | `[priority, sessions, unopened_first, urgency]` | 新会话排序规则列表，亦支持逗号分隔字符串 |
| `urgency_minutes_per_percent` | `1` | 计算紧迫时间时每 1% 剩余额度折算的分钟数；`0` 等价于按重置时间排序 |
| `plan_multipliers` | `{}` | 按账号 ID（可从面板复制）配置套餐倍数。Plus / Team 标准席位为 `1`（未配置时默认 `1`），Team Pro 席位与 Pro $100 为 `10`，Pro $200 为 `20`，Pro $500 为 `50`。仅影响 `urgency` 与 `remaining`；亦支持 `id1=10, id2=20` 格式 |
| `session_ttl` | `30m` | 会话滑动粘性窗口；闲置超时后释放绑定，不再计入该账号活跃会话数 |
| `state_path` | `codex-reorder-state.json` | 会话绑定、额度快照与决策记录的持久化路径（相对 CPA 工作目录）；留空则禁用持久化，重启后全部丢失 |
| `manage_api_keys` | `false` | 是否将配置文件中的 `codex-api-key` 纳入插件调度 |
| `stats_interval` | `off` | 定期输出 `stats` 聚合日志的间隔（如 `15m`，最小 `1m`），默认关闭，见[日志](#日志) |
| `warmup_enabled` | `false` | 是否启用自动开窗（开启后会实际发送请求） |
| `warmup_model` | `gpt-6-luna` | 开窗请求使用的模型 |
| `warmup_reasoning_effort` | `low` | 开窗请求的思考强度（CPA 内置的 Codex 模型无法关闭思考，`low` 消耗最低） |
| `warmup_hours` | `09:00-22:00` | 允许自动开窗的时段，支持跨零点（如 `22:00-02:00`）；`00:00-24:00` 表示全天 |
| `warmup_timezone` | `Asia/Shanghai` | `warmup_hours` 所用时区 |
| `warmup_delay` | `20m-90m` | 周额度停止计时后的随机等待区间；`0s` 表示立即开窗 |
| `warmup_spacing` | `0s` | 任意两次自动开窗（不区分账号）之间的随机间隔，如 `5m-20m`；`0s` 表示不限 |
| `warmup_max_per_account_per_day` | `2` | 单账号每日自动开窗次数上限（含成功与失败，不含手动开窗） |

> 旧版本配置项 `max_sessions_per_account`、`failover_rebind_after`、`warmup_dry_run`、`warmup_max_per_day` 已移除；保留在配置中不会报错，仅在启动日志和面板中提示清理。

## Web 面板

地址：`https://<CPA地址>/v0/resource/plugins/codex-reorder/dashboard`，使用 CPA 管理密钥登录，每 5 秒自动刷新。

- **全局概览**：当前生效的排序规则、下一条新会话将分配给谁及原因、配置提醒、开窗状态。
- **账号列表**：按"下一条新会话的分配顺位"排列，展示状态、活跃会话数、周额度（已用比例与重置时间，或"未开窗"）、紧迫时间、5 小时额度与生图额度（仅展示）、最近一次分配与失败、额度查询结果。参与排序的列在表头标注序号；点击账号可展开其绑定的会话。
- **编辑排序**：增删规则、拖拽调整顺序，修改紧迫系数与套餐倍数。编辑期间右侧实时对比当前与新规则的排序差异（仅预览，不落盘）。点击"保存并生效"后先列出改动供确认，再通过 CPA 插件配置接口写回 `config.yaml`（保留注释）并触发热重载，仅影响后续新会话。
- **开窗设置**：自动开窗的全部参数，输入时即时校验格式，保存流程同上。
- **运维操作**：全局**刷新额度**，以及每个账号的**查询**、**立即开窗**按钮。
- **会话绑定**：每个会话所绑账号、绑定时长、闲置时长、剩余 TTL、请求数与成功数。
- **决策日志**：近期新会话、换号、生图等分配决策，每条附带原因与当时的排名。

**安全模型**：CPA 的插件资源路径（`/v0/resource/...`）**无需认证即可访问**，因此面板 HTML 本身只是空壳，不含任何业务数据；所有数据拉取、预览、保存与查询均经由需要管理密钥的 Management API 完成。能在面板上保存设置的人，本就能修改 CPA 的全部配置，面板不会放大任何权限。管理密钥仅保存在当前标签页的 `sessionStorage` 中，关闭即清除；会话 ID 仅存哈希，不记录原文。

## 自动开窗

Codex 的周额度窗口在**首次使用**时才开始计时，7 天后重置。若账号重置后长期无人使用，这段空转时间就是白白损失的额度。"开窗"即向此类账号发送一个极小的请求，使其周额度开始计时。

默认关闭。开启 `warmup_enabled: true` 后：

- **触发时机**：周额度停止计时后，随机等待 `warmup_delay`（默认 20–90 分钟）再开窗；若落点在 `warmup_hours` 之外，则顺延至下一个允许时段内的随机时刻。等待期间若已有正常流量开窗，则自动取消。
- **频率与兜底**：每分钟检查一次，单次最多开一个账号，可通过 `warmup_spacing` 进一步拉开间隔。同一个未开窗周期只自动尝试一次，失败则顺延至次日，并受 `warmup_max_per_account_per_day` 上限兜底。
- **执行方式**：通过 CPA 的 `host.model.execute` 锁定目标账号发送，复用该账号自身的令牌、代理及 CPA 的 Codex 客户端伪装，与正常请求无异。提示词每次随机生成，形如 `Reply with 5181.`。
- **跳过条件**：被禁用、处于冷却、周额度已耗尽的账号，以及 `order` 中配置了 `unopened_last`（表示有意不开窗）时，均不自动开窗。
- **不计入正常流量**：开窗请求不建立会话绑定，不计入分配统计。
- **手动开窗**：面板上未开窗的账号提供**立即开窗**按钮，不受开关、时段、间隔与每日上限限制。

> **使用了重置卡？** 重置后的周额度同样处于"未开窗"状态，但插件要等该账号下一次有请求或被查询时才能感知。先在面板上点击该账号的**查询**，待其显示"未开窗"后，再点击**立即开窗**即可。

## 主动查询额度

插件日常通过请求的响应头被动更新额度。刚部署、新增账号，或账号同时在其他地方使用时，数据可能缺失或过时，可通过面板的**刷新额度**（全部）或单账号**查询**主动同步。

查询由面板通过 CPA 的 `api-call` 接口请求 `https://chatgpt.com/backend-api/wham/usage`，**令牌由 CPA 填充（必要时自动刷新），并走该账号自身的代理**，与 CPA Manager Plus 查询额度的路径完全一致，查询结果再交由插件解析。

- 仅在手动点击时执行，无后台定时轮询。串行查询，每个账号间隔 2 秒（10 个账号约半分钟），查询完成前请勿关闭面板；全部刷新时自动跳过 10 分钟内已有数据的账号。
- 该接口只读，不消耗额度，也不会触发开窗。
- 查询失败（如 401）仅记录错误，不覆盖已有额度快照。
- 插件本身不发起任何网络请求，也不接触令牌与代理。CPA 虽然提供了供插件使用的额度接口，但 `.so` 插件经由该接口发出的请求不走账号代理（会从服务器 IP 直连），因此未采用。

## 生图请求路由

发往 `/v1/images/generations` 与 `/v1/images/edits` 的请求走独立通道：

- **无状态轮询**：生图没有上下文缓存需要保护，每次请求分配给"最久未分配生图"的账号，均匀分摊，不建立会话绑定。
- **独立额度追踪**：生图响应头中的额度信息（`x-codex-active-limit: imagegen_premium`，24 小时窗口）独立于对话的周额度与 5 小时额度。插件将其记录为账号的"生图额度"并在面板展示，**不会**覆盖周额度。由于没有接口可主动查询生图额度，面板显示的是最近一次生图时的数据。
- **耗尽跳过**：优先跳过生图额度已满的账号，其次跳过周额度耗尽的账号；仅剩此类账号时照常分配。
- **credits 标记**：若响应显示账号有额外 credits，面板会标注"有 credits"。

## 日志

### 结构化事件日志

插件将事件写入 CPA 主日志（开启 `logging-to-file` 时为 `logs/main.log`），随 CPA 一同轮转，不另建文件。格式统一为 `codex-reorder <类型> <JSON>`，时间均为 UTC。写入经由后台异步队列，不阻塞选号路径。

| 事件类型 | 触发时机 | 主要内容 |
|---|---|---|
| `pick` | 新会话、换号、`pinned`、`held`、生图 | 目标账号、原账号、模型、生效规则、决策原因、前三名候选排名 |
| `window_end` | 账号周额度窗口结束（每个窗口一行） | 结束前最后观测到的使用率与未用比例（`unused`） |
| `image_usage` | 每次生图响应 | 账号、模型、请求状态及原始额度响应头 |
| `warmup` | 每次开窗尝试 | 账号、执行结果、模型、提示词、HTTP 状态码等 |
| `probe` | 每次额度查询 | 账号、窗口状态或错误信息 |
| `stats` | **默认不输出**，仅在设置 `stats_interval` 后 | 周期内各类分配计数、按状态码统计的失败数、各账号会话数与额度快照（每小时一行含全部账号，其余仅含周期内有活动的账号） |

- 命中粘性的既有会话请求（占绝大多数）不逐条记录，仅在 `stats` 中汇总计数。`stats` 单行约 2–3 KB，若每 5 分钟输出一行，可占到 CPA 日志的三成左右，因此默认关闭；排查问题时设为 `15m` 即可。
- 新会话的 `pick` 若携带来源信号，会附带 `lineage` 字段：父会话哈希、父会话当前绑定的账号、是否为 Codex 子代理等。目前仅记录，不参与调度。
- `rebind`、`held`、`pinned` 的 `failover` 字段记录参与选号的候选数量、原账号是否在候选中、CPA 是否指定了固定账号，以及原账号已知耗尽的窗口（`5h`、`weekly`）。若 CPA 提供 `trace_id`，可用其末 8 位关联主日志中的上游报错；若无该字段，可按时间戳、模型和账号 ID 对照。

常用分析命令：

```bash
# 各账号周额度窗口结束时的浪费比例
grep -ah 'codex-reorder window_end ' logs/main*.log | sed 's/.*window_end //' | jq -c '{auth, reset_at, used_pct, unused}'
# 各时段粘性命中与新会话数（需开启 stats_interval）
grep -ah 'codex-reorder stats ' logs/main*.log | sed 's/.*stats //' | jq -c '{to, picks, new: .kinds.new, sticky: .kinds.sticky}'
# 近期生图额度记录
grep -ah 'codex-reorder image_usage ' logs/main*.log | tail
```

## 升级与热替换

### 插件热升级（无需重启 CPA）

CPA 支持插件热替换：重新加载配置时若检测到插件文件变化，会先停用旧实例再加载新实例。会话绑定通过状态文件延续到新版本。

1. 将新版本 `codex-reorder-v<版本号>.so` 放入插件目录（建议先以临时文件名上传，完成后再重命名）。
2. 将旧 `.so` 移出插件目录备份，以便回滚。
3. **原地修改** `config.yaml`（例如调整一行注释）以触发 CPA 重载。请勿采用"写入新文件再 rename 覆盖"的方式，CPA 监听的是文件本身。
4. 确认日志出现 `plugin hot reloaded plugin_id=codex-reorder active_version=<新> retired_version=<旧>`，以及新版本的 `configured` 记录。

回滚执行相反步骤即可。

> CPA 不会真正卸载被替换的旧实例，它会驻留在进程中直至 CPA 重启。本插件自 `0.6.0` 起在被替换时主动停止全部后台任务，并阻止旧实例覆盖新实例写入的状态文件，因此可安全热替换。从 `0.5.x` 及更早版本升级时，请重启一次 CPA。

### CPA 主程序升级

只要插件 C ABI 未变化，现有 `.so` 通常可直接沿用。如需针对新版本重新编译，更新 `go.mod` 中 `github.com/router-for-me/CLIProxyAPI/v8` 的版本后执行：

```bash
go mod tidy && make test && make smoke && make build
```

## 使用注意事项

- **冷启动无额度数据**：每个账号需等到首个请求返回才能获知额度，此后随状态文件持久化，重启不丢失。如需立即查看，点击面板的**刷新额度**。
- **CPA 原生粘性日志消失**：插件接管后，CPA 原有的 `session-affinity: cache hit / new binding` 日志不再对 Codex 请求输出，请查阅插件自身的事件日志。
- **异常不中断服务**：若插件崩溃，CPA 会自动熔断并退回内置调度，进行中的 Codex 会话会被重新分配一次。
- **子代理按独立会话处理**：若中转层（如 new-api）未透传父子会话请求头，插件无法识别子代理归属，会将其作为独立会话调度。
- **Fork 发布**：CPA 会拒绝仓库地址为空的插件。自行 fork 发布时，请将 `plugin.go` 中的 `pluginRepository` 改为你的仓库地址。
- **与 CPA Manager Plus 兼容**：与其"额度冷却自动化"无冲突，被禁用的账号不会进入候选列表，相关会话会自动故障切换。

## 设计取舍

**为什么插件要自行维护会话绑定？** CPA 选号时先询问调度插件，插件不处理时才轮到 CPA 原生粘性。插件一旦选定账号，CPA 的粘性逻辑整段跳过，也不会记录此次绑定。插件与 CPA 是相互独立的运行时，插件读不到 CPA 内存中的绑定表，CPA 也没有提供列出或写入该表的接口，因此只能由插件自行维护。所幸最复杂的部分仍由 CPA 处理好后交给插件：会话识别（CPA 从 `prompt_cache_key` 等推导会话 ID）、可用性过滤（候选列表已过滤）、额度数据（随用量记录一同传入）。自行维护的额外好处是，面板可以准确列出每个账号承载的会话。

**为什么默认先分散、再看额度？** 单个账号同时承载过多会话风险较高，这是硬约束。先分散还能避免某个账号被率先用尽、迫使其上的会话集体换号。

**为什么优先使用未开窗的账号？** 周额度按时间持续发放：窗口一个接一个开启，每 7 天获得一份完整额度，两个窗口之间的空档就是损失。代价是会话较少时，临近过期的账号可能分配不到。如果额度对你而言不是瓶颈，可改用 `unopened_last`。

**为什么用紧迫时间而非单纯的重置时间？** 若只看重置时间，开窗仅相差几秒的两个账号（一波新会话同时到达时很常见）会被严格分出先后，早几秒的账号整周被多用、率先耗尽，会话被迫换号。紧迫时间把剩余额度折算为时间：重置时间接近时余量多者优先，相距较远时临期者优先，两者之间平滑过渡。

**为什么不支持自定义规则表达式？** 表达式很容易配置出自相矛盾、或把会话全部压到一个账号上的规则，也会让"为什么选了这个账号"难以解释。如需新的排序维度，应作为内置规则加入。

**有意不做的功能：**

- **根据 5 小时用量提前避开账号**："即将触达上限"难以准确判断，还会引发来回切换；真正触达时 CPA 会自行冷却该账号。
- **周额度即将耗尽时拒绝新会话**：这与"不浪费临期额度"的目标正好相反。

## 开发与测试

```bash
make test    # 运行单元测试（启用 -race 检测）
make smoke   # 端到端冒烟测试：在真实 CPA 进程中加载插件并对接模拟 Codex 上游
make build   # 编译 dist/codex-reorder.so
```

`make smoke` 会自动查找 CPA 可执行文件，找不到时从 `CPA_SRC`（默认 `../CLIProxyAPI`）编译。它覆盖的链路包括：新会话分散、紧迫度排序、粘性保持、429/502 故障切换且不回切、CPA 重启后绑定恢复、面板预览与保存、带前缀模型、自动开窗、额度查询，以及 API Key 交还 CPA 等。由于 CPA 授权文件无法指向本地模拟上游，冒烟测试中的模拟账号实为配置文件中的 API Key，因此冒烟配置开启了 `manage_api_keys`。

如需保留冒烟环境以手动调试面板：

```bash
go run ./test/smoke -keep
```

### 发布

发布包覆盖 Apple Silicon macOS、Linux amd64/arm64 和 Windows amd64/arm64。每包命名为 `codex-reorder_<版本>_<系统>_<架构>.zip`，根目录只包含对应的 `codex-reorder.dylib`、`codex-reorder.so` 或 `codex-reorder.dll`。五个包共用一份 `checksums.txt`。正式发布由 GitHub Actions 的 **Release** 工作流完成：

1. 确认 `plugin.go` 中的 `pluginVersion` 已更新为新版本并推送。
2. 在 Actions 中手动运行 Release，填写版本号（不带 `v`）。`verify` 模式只构建和校验，产物作为工作流附件提供下载；`publish` 模式会额外创建 GitHub Release `v<版本>`。

工作流在目标系统和架构上用 CPA 实际加载插件，并通过模拟上游验证调度、会话粘性及额度读取。Linux 库在 manylinux2014 容器里编译和加载，glibc 上限为 2.17。打包后再通过 CPA 的插件安装器校验和安装每个包，并检查库格式与架构。

本地有 Docker 时也可以手动构建（只能构建与本机相同的架构）：

```bash
make release-lib                                   # dist/lib/linux_<本机架构>/codex-reorder.so
make release-package RELEASE_PLATFORMS=linux/amd64 # dist/release/ 下的 zip 与 checksums.txt
```

CPA 插件商店要求额外提供 Intel macOS（`darwin/amd64`）。本项目选择独立发布，商店申请状态见 [PR #386](https://github.com/router-for-me/CLIProxyAPI-Plugins-Store/pull/386)。
