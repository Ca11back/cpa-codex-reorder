# codex-reorder

一个 [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)（下文简称 CPA）插件，专门负责“这个 Codex 请求该交给哪个账号”。

如果你在 CPA 里挂了好几个 Codex 账号（OAuth 或 PAT 授权文件），它帮你做到三件事：

- **同一个对话一直用同一个账号**，不来回换号，提示词缓存不会丢。
- **新对话尽量分散到不同账号**，不让某一个号同时扛太多对话。
- **快过期的额度优先用掉**。各账号的周额度到期时间不一样，过期就作废，插件会让“快到期、还剩很多”的号先干活。

另外还附带一个网页面板（看每个号的额度、绑了哪些对话、为什么这么分），以及可选的“自动开窗”和手动刷新额度。

> CPA 配置文件里写的 Codex API Key（`codex-api-key`）默认不归插件管，仍由 CPA 自己选。原因见下文“只管账号，不管 API Key”。

## 它是怎么选账号的

### 老对话：不换号

一个对话第一次来的时候被分到某个号，之后的请求都走这个号，直到它闲置超过 `session_ttl`（默认 30 分钟）。

只有这个号**这一次实在用不了**时才换：出错了 CPA 正在换号重试、号在冷却、被禁用、不支持这个模型、或者已知额度用完。换了就留在新号上，旧号恢复了也不换回去。这和 CPA 自带粘性的默认行为（`session-affinity-rebind-on: any`）一样。

> 为什么换了就不回去：来回换号每次都要多一次失败重试，到了新号缓存又是空的。实测“临时转走、恢复后转回”会让一个对话半小时里在 4 个号之间跳 7 次，不如一次换到底。

### 新对话：按一张排序表挑号

新对话来了，插件把所有可用的号排个队，第一名接单。怎么排由 `order` 决定：先比第一条规则，比不出高下再比第二条，以此类推。

| 规则 | 意思 |
|---|---|
| `sessions` | 手上对话少的优先。用来分散压力 |
| `priority` | CPA 里设的账号优先级高的优先。所有号优先级一样时这条不起作用 |
| `unopened_first` | 周额度还没开始计时的号优先（见下面“开窗”） |
| `unopened_last` | 和上一条相反：没开始计时的号放最后 |
| `urgency` | 最“紧迫”的优先（见下面） |
| `reset` | 周额度先重置的优先 |
| `remaining` | 周额度剩得多的优先 |

默认是 `priority, sessions, unopened_first, urgency`，翻译过来就是：

1. 先听 CPA 优先级的；
2. 再把对话平均分开；
3. 都一样闲的话，先把还没开始计时的号用起来（不用就白白少拿额度）；
4. 最后，谁的额度最紧迫谁先用。

**什么叫“紧迫”？** 光看哪个号先重置不够：A 10 小时后重置但只剩 5%，B 晚 10 分钟重置却剩 90%，显然 B 更急，因为它那么多额度得赶紧用。插件的算法是：

> 紧迫时间 = 周额度重置时间 − 剩余百分比 × 套餐倍数 × 1 分钟

剩得越多，紧迫时间就越往前提。上面的例子里 A 折算成 9 小时 55 分，B 折算成 8 小时 40 分，B 先用。而如果 A 明天重置、B 后天重置，差距大到剩余多少都追不上，那还是 A 先。“1 分钟”这个系数可以用 `urgency_minutes_per_percent` 调，设成 0 就等于只看重置时间。

几点补充：

- **规则顺序完全由你定。** 但 `urgency`、`reset`、`remaining` 是连续的数值，几乎不会打平，放在它们后面的规则基本轮不到。
- **不放 `sessions` 的话**，新对话会扎堆到少数号上，插件会在日志和面板上提醒你。
- **已知额度用完的号永远排最后**，它只会回 429。这条不能改。
- **被禁用、在冷却、不支持该模型的号**，CPA 根本不会交给插件。
- **刚分到对话、还没拿到额度数据的号**，先当它“刚开始计时、剩 100%”，免得下一个新对话又挤上去。
- **5 小时额度不参与排序**，撞到 5 小时上限 CPA 会自己冷却那个号。

### 只管账号，不管 API Key

配置文件里的 Codex API Key 没有周额度和 5 小时窗口，上面那些规则对它们没意义。更麻烦的是，没有额度数据的 Key 会被当成“还没开始计时”，按默认规则排到最前面，把新对话引到按量计费的 Key 上。所以默认：

- 候选里有账号也有 Key：只在账号里挑；
- 只剩 Key 能用：整个交还给 CPA；
- 某个 Key 的优先级比所有账号都高：也交还给 CPA，因为 CPA 自己就会先用它。

真想让插件连 Key 一起排，设 `manage_api_keys: true`。

### 几种特殊请求

- **没有会话 ID 的请求**：照样按排序表选号，但不建立绑定。（经 new-api 之类中转过来的 Codex 请求一般带 `prompt_cache_key`，CPA 会据此算出会话 ID。）
- **CPA 只给了原来那个号**：比如在 Codex 的 websocket 长连接里，CPA 把整条连接固定在一个号上。这时就算原号额度用完了也没别的号可换，插件这次照样走原号、不改绑定，记作 `held`。等上游回 429、连接断开、客户端重连，下一次请求再正常换号。
- **带前缀的模型名**（`<账号前缀>/<模型>`）：CPA 只会给出前缀对得上的号，插件就用它，但不改这个对话原来的绑定（记作 `pinned`），之后不带前缀的请求还回原号。这和 CPA 自己“按对话 + 模型分别绑定”的效果一样。
- **生图请求**：单独处理，见[生图请求](#生图请求)。
- **其他 provider，或者 Codex 和别的 provider 混在一起的请求**：插件不管，交还给 CPA。

## 快速开始

### 需要什么

- CPA v8.0.61 或更新（插件 C ABI 1）。实际在 v8.0.61 到 v8.0.75 上跑过。
- Linux，Go 1.26 以上，以及 cgo 用的 gcc。

### 编译

```bash
make build
```

产物是 `dist/codex-reorder.so`。amd64 上按最基础的指令集（`GOAMD64=v1`）编译，老 CPU 和虚拟机也能加载。

### 安装

1. **停掉别的 Codex 调度插件。** CPA 同一时间只认一个调度插件。如果你装了别的（比如 `codex-quota-scheduler`），把它的 `enabled` 设成 `false`，或者直接把它的 `.so` 拿走。有些调度插件不负责调度时也还在观察用量、拦截请求，所以一定要关干净。
2. **把 `codex-reorder.so` 放进 CPA 的插件目录。** CPA 先找 `plugins/linux/amd64/`，再找 `plugins/`。文件名决定插件 ID，`codex-reorder.so` 和 `codex-reorder-v0.6.5.so` 都算 `codex-reorder`。`config.yaml` 里没有它的配置时不会加载，所以可以先放文件、以后再开。
3. **改 CPA 的 `config.yaml`**，照着 [config.example.yaml](config.example.yaml) 加上插件配置。CPA 会自动重新加载，不用重启。
4. **看日志确认。** 应该出现一行 `codex-reorder 0.6.5 configured: order=...`。有配置问题的话紧跟着会有一条 `codex-reorder config:` 警告。
5. **打开面板**：`https://<你的 CPA 地址>/v0/resource/plugins/codex-reorder/dashboard`，输入 CPA 管理密钥。

> **启用那一刻正在进行的对话，每个会被重新分配一次**，因为插件看不到 CPA 原来的绑定。建议挑流量少的时候启用。
>
> 想停用：把 `enabled` 改成 `false`，CPA 卸下插件，立刻回到它自带的粘性选号。

如果你之前用的是 CPA 自带的粘性，记得把 `session_ttl` 设成和原来的 `routing.session-affinity-ttl` 一样（比如 `1h`），行为才一致。插件接管后，CPA 的这个设置对 Codex 不再生效（对其他 provider 照常有效，建议保持开启）。

## 配置项

都写在 CPA `config.yaml` 的 `plugins.configs.codex-reorder` 下面。排序和开窗相关的设置也可以直接在面板上改。

| 配置 | 默认 | 说明 |
|---|---|---|
| `order` | `[priority, sessions, unopened_first, urgency]` | 新对话的排序规则，见上文。也可以写成逗号分隔的字符串 |
| `urgency_minutes_per_percent` | `1` | 算“紧迫”时，剩余每 1% 折多少分钟。`0` 等于只看重置时间 |
| `plan_multipliers` | 空 | 套餐倍数，按账号 ID（面板上能复制）填。Plus / Team 普通席位是 1，Team Pro 席位和 Pro 100 刀是 10，Pro 200 刀是 20，500 刀是 50。没写的按 1。只影响 `urgency` 和 `remaining`。也可以写成 `id=10, id2=20` |
| `session_ttl` | `30m` | 对话闲置多久算结束。结束后不再占这个号的“对话数” |
| `state_path` | `codex-reorder-state.json` | 绑定关系、额度快照、分配记录存哪（相对 CPA 工作目录）。留空就不保存，重启后全部丢失 |
| `manage_api_keys` | `false` | 要不要连配置文件里的 Codex API Key 一起调度 |
| `stats_interval` | `off` | 多久往日志写一行统计，比如 `15m`（最短 `1m`）。默认不写，见[日志](#日志) |
| `warmup_enabled` | `false` | 自动开窗。打开就会真的发请求，见[自动开窗](#自动开窗) |
| `warmup_model` / `warmup_reasoning_effort` | `gpt-6-luna` / `low` | 开窗请求用的模型和思考强度。CPA 内置的 Codex 模型不能关思考，`low` 最省 |
| `warmup_hours` / `warmup_timezone` | `09:00-22:00` / `Asia/Shanghai` | 只在这个时段内开窗，可以跨零点（如 `22:00-02:00`）。`00:00-24:00` 表示不限 |
| `warmup_delay` | `20m-90m` | 周额度停止计时后，随机等多久再开。`0s` 表示马上开 |
| `warmup_spacing` | `0s` | 两次开窗之间随机隔多久（不管是哪个号），比如 `5m-20m`。`0s` 表示不隔 |
| `warmup_max_per_account_per_day` | `2` | 每个号每天最多自动开几次（成功失败都算，手动开窗不算） |

旧版本里的 `max_sessions_per_account`、`failover_rebind_after`、`warmup_dry_run`、`warmup_max_per_day` 已经去掉了。配置里留着也不会报错，只会提醒你可以删。

## 面板

地址：`https://<你的 CPA 地址>/v0/resource/plugins/codex-reorder/dashboard`，需要 CPA 管理密钥。每 5 秒自动刷新。

- **顶部**：现在用的排序规则、下一个新对话会分给谁以及为什么、配置提醒、开窗状态。
- **账号列表**：按“下一个新对话分给谁”排好。每个号能看到：状态、手上几个对话、周额度（用了多少、什么时候重置，或者“还没开始计时”）、紧迫时间、5 小时额度和生图额度（只展示）、最近一次分配和失败、额度查询。参与排序的列在表头标了序号。点一个号可以展开它身上的对话。
- **编辑排序**：加规则、删规则、拖动调先后，还能改紧迫系数和套餐倍数。改的时候右边实时对比“现在”和“改完”两种排法，只算不动。点“保存并生效”会先列出改动让你确认，然后通过 CPA 自带的插件配置接口写进 `config.yaml`（保留注释），CPA 自动重载。只影响之后的新对话。
- **开窗设置**：自动开窗的所有参数，输入时就检查格式，保存流程同上。
- **刷新额度** 和每个号的 **查询**、**立即开窗** 按钮。
- **对话绑定**：每个对话绑在哪个号、绑了多久、闲了多久、还剩多久过期、请求数和成功数。
- **分配记录**：最近的新对话、换号、生图等决定，每条都写了原因和当时的排名。

**安全性**：CPA 的插件资源页（`/v0/resource/...`）**不需要登录就能打开**，所以这个页面本身只是个空壳，不含任何数据。所有数据、预览、保存、查询都走需要管理密钥的接口。能在面板上保存设置的人，本来就能改 CPA 的全部配置，面板没有放大任何权限。管理密钥只存在当前浏览器标签页里（`sessionStorage`），关掉就没了。会话 ID 只存哈希，不存原文。

## 自动开窗

Codex 的周额度窗口要等**第一次使用**才开始计时，计时 7 天后重置。如果一个号重置后一直没人用，这段空着的时间就是白白少拿的额度。“开窗”就是给这种号发一个极小的请求，让它的周额度开始计时。

默认关闭。打开后：

- **什么时候开**：周额度停止计时后，随机等 `warmup_delay`（默认 20–90 分钟）再开。落在 `warmup_hours` 之外的，顺延到下一个允许时段开始后的随机时刻。等待期间要是有正常请求已经把窗口打开了，就不开了。
- **开多频繁**：每分钟检查一次，一次最多开一个号，可以用 `warmup_spacing` 再加间隔。同一次“没开始计时”只自动开一次，失败了顺延到第二天。每号每天最多 `warmup_max_per_account_per_day` 次兜底。
- **怎么开**：通过 CPA 的 `host.model.execute` 锁定这个号发出，走这个号自己的令牌、代理和 CPA 的 Codex 客户端伪装，和正常请求一模一样。提示词每次随机生成，形如 `Reply with 5181.`。
- **不开的情况**：被禁用、在冷却、额度已用完的号；以及排序里用了 `unopened_last`（表示你有意不开窗）。
- **不算正常流量**：开窗请求不建立绑定，不计入分配次数。
- **手动开窗**：面板上没开始计时的号有“立即开窗”按钮，不受开关、时段、间隔和每日上限限制。

> **用了重置卡怎么办？** 重置后的周额度也是“未开始计时”状态，但插件要等这个号下次有请求或下次查询才会知道。在面板上对这个号先点“查询”，它会显示“未开窗”，再点“立即开窗”就行。

## 刷新额度

插件平时从每个请求的响应头里拿额度数据。刚装好、新加的号、或者号也在别的地方用时，数据会缺或者过时。面板上的 **刷新额度**（全部）和每个号的 **查询**（单个）可以手动补上。

它是这样查的：面板通过 CPA 自己的 `api-call` 接口，请求 `https://chatgpt.com/backend-api/wham/usage`。**令牌由 CPA 填（需要时还会刷新），走这个号自己的代理**，和 CPA Manager Plus 查额度完全是同一条路。查到的结果交给插件解析。

- 只有你点按钮才会查，没有定时轮询。一次查一个号，间隔 2 秒，10 个号大约半分钟，查完之前别关面板。全部刷新时，10 分钟内已有数据的号会跳过。
- 这个接口只读，不消耗额度，也不会开窗。
- 查询失败（比如 401）只记一下错误，已有数据不动。
- 插件自己不发任何网络请求，也不碰令牌和代理。CPA 其实也有给插件用的额度接口，但 `.so` 插件通过它发的请求不走账号代理（会从服务器 IP 直连），所以没用它。

## 生图请求

发到 `/v1/images/generations` 或 `/v1/images/edits` 的请求，插件单独处理：

- **轮流分配，不绑定。** 生图没有对话上下文，也没有缓存可保，所以每张图都分给“最久没分到生图”的号，把生图均匀摊开。
- **生图有自己的每日额度。** 生图响应里的额度信息（`x-codex-active-limit: imagegen_premium`，24 小时窗口）和对话的周额度、5 小时额度是分开的。插件会把它记成这个号的“生图额度”，显示在面板上，**不会**拿去覆盖周额度。没有接口能查生图额度，所以显示的是最近一次生图时的数据。
- **跳过用满的号。** 生图额度已知用满的号先跳过，其次跳过周额度用完的号；只剩这些号时照常分配。
- 响应里显示这个号有额外 credits 的话，面板上会标“有 credits”。

## 日志

插件把事后分析用的信息写进 CPA 自己的日志（开了 `logging-to-file` 时是 `logs/main.log`），跟着 CPA 一起轮转，不另建文件。每行长这样：`codex-reorder <类型> <JSON>`，时间都是 UTC。

| 类型 | 什么时候写 | 写了什么 |
|---|---|---|
| `pick` | 新对话、换号、`pinned`、`held`、生图 | 选了哪个号、原来是哪个号、模型、哪条规则起的作用、原因、排名前三的号 |
| `window_end` | 某个号的周额度窗口结束时，每个窗口一行 | 结束前最后看到用了多少、浪费了多少（`unused`） |
| `image_usage` | 每个生图响应 | 账号、模型、成功与否、原样的额度响应头 |
| `warmup` | 每次开窗尝试 | 账号、结果、模型、提示词、HTTP 状态等 |
| `probe` | 每次额度查询 | 账号、查到的窗口状态，或者错误 |
| `stats` | **默认不写**，设了 `stats_interval` 才写 | 这段时间的分配次数（按类型分）、失败按状态码分、各号的对话数和额度。每小时一行带全部账号，其他行只带这段时间里有动静的号 |

老对话继续用原号的请求（绝大多数请求都是这种）不逐条记，只在 `stats` 里计数。`stats` 每行有两三 KB，每 5 分钟一行的话能占到 CPA 日志的三成，所以默认关掉；要排查问题时设成 `15m` 就够了。

新对话的 `pick` 行如果带了来源信息，会有 `lineage` 字段：父对话的哈希、父对话现在绑在哪个号、是不是 Codex 的子代理等。目前只记录，不影响选号。

几个常用的分析命令：

```bash
# 每个周额度窗口结束时浪费了多少
grep -ah 'codex-reorder window_end ' logs/main*.log | sed 's/.*window_end //' | jq -c '{auth, reset_at, used_pct, unused}'
# 每段时间的老对话命中和新对话数（需要开 stats_interval）
grep -ah 'codex-reorder stats ' logs/main*.log | sed 's/.*stats //' | jq -c '{to, picks, new: .kinds.new, sticky: .kinds.sticky}'
# 最近的生图额度
grep -ah 'codex-reorder image_usage ' logs/main*.log | tail
```

插件写日志走一个后台队列，不会卡住选号。CPA 不把请求 ID 交给插件，所以这些行的请求 ID 一栏是 `--------`，需要按时间和账号去对 CPA 自己的日志。

## 升级

### 升级插件（不用重启 CPA）

CPA 支持插件热替换：重新加载配置时，如果插件文件换了，会先让旧插件停下来，再加载新的。对话绑定通过状态文件带过去。

1. 把新的 `codex-reorder-v<新版本>.so` 放进插件目录（建议先用临时文件名上传，传完再改名）。
2. 把旧的 `.so` 移出插件目录，留着回滚用。
3. 让 CPA 重新加载一次配置：随便改一下 `config.yaml`，比如改一行注释。**要原地改**，别用“写个新文件再改名”的方式，CPA 盯的是这个文件本身。
4. 日志里应该出现 `plugin hot reloaded plugin_id=codex-reorder active_version=<新> retired_version=<旧>`，以及新版本的 `configured` 行。

回滚就是反过来再做一遍。

> CPA 不会真正关掉被替换下来的旧插件，它一直留在进程里直到 CPA 重启。0.6.0 起插件会在被替换时自己停掉所有后台任务，并且旧实例不能再覆盖新实例写的状态文件，所以热替换是安全的。从 0.5.x 或更早的版本升上来，请重启一次 CPA。

### CPA 升级了

只要插件 ABI 没变，旧插件一般能继续用。想稳妥一点就按新版本重新编译：把 `go.mod` 里的 `github.com/router-for-me/CLIProxyAPI/v8` 改成对应版本，`go mod tidy`，然后 `make test`、`make smoke`、`make build`。

## 注意事项

- **刚装好时没有额度数据。** 每个号要等第一个请求回来才知道它的额度，之后存在状态文件里，重启不丢。想马上看到，点面板的“刷新额度”。
- **CPA 自己的粘性日志会消失。** 插件接管后，CPA 原来每个请求一行的 `session-affinity: cache hit / new binding` 不再出现在 Codex 请求上，对应信息看插件的日志。
- **插件崩了不会断服务。** CPA 会熔断插件、退回内置调度，Codex 对话会被重新分配一次。
- **子代理按独立对话处理。** 中转层（比如 new-api）默认不透传父子关系的请求头时，插件分不出子代理属于哪个对话。
- **插件元数据里的仓库地址不能为空**，否则 CPA 拒绝加载。自己 fork 发布时，把 `plugin.go` 里的 `pluginRepository` 改成你的仓库地址。
- **和 CPA Manager Plus 的“额度冷却自动化”不冲突。** 它禁用的号自然不在候选里，对话会跟着换号。

## 为什么这么设计

**为什么插件要自己记“哪个对话绑在哪个号”？** CPA 选号时先问调度插件，插件不管才轮到 CPA 自带的粘性。插件一旦选了号，CPA 的粘性逻辑整段跳过，也不会记录这次绑定。插件和 CPA 是两个独立的运行时，插件读不到 CPA 内存里的绑定表，CPA 也没有接口能列出或写入这张表。所以插件只能自己记。好在最难的几件事还是 CPA 做好了交过来的：会话识别（CPA 从 `prompt_cache_key` 等算出会话 ID）、哪些号能用（候选列表已经过滤好）、额度数据（随用量记录一起交给插件）。自己记还有个好处：面板能准确列出每个号身上有哪些对话。

**为什么默认先分散、再看额度？** 一个号上同时跑太多对话风险高，这是硬约束。先分散也能避免把某一个号先用光、逼着对话换号。

**为什么“没开始计时”的号优先？** 周额度是按时间持续发放的：窗口一个接一个地开，每 7 天就拿一份完整额度；中间空着不开的时间就是少拿的。代价是对话少的时候，快到期的号可能分不到。如果额度对你不是瓶颈，可以改成 `unopened_last`。

**为什么用“紧迫”而不是单纯看重置时间？** 只看重置时间的话，开窗只差几秒的两个号（一波新对话同时进来时很常见）会被严格分出先后，早几秒的那个号整周都被多用，先用光，对话被迫换号。“紧迫”把剩余额度折算成时间，重置时间接近时剩得多的先用，差得远时先到期的先用，中间是平滑过渡的。

**为什么不能写自定义规则表达式？** 表达式很容易配出自相矛盾、或者把对话全压到一个号上的规则，也会让“为什么选了这个号”说不清。需要新规则时，加成内置规则。

**故意没做的：**

- 按 5 小时用量提前避开某个号：“快撞上了”判断不准，还会来回切换。撞上了 CPA 会自己冷却。
- 周额度快用完就不接新对话：这和“不浪费快过期的额度”正好相反。

## 开发

```bash
make test    # 单元测试（带 race 检测）
make smoke   # 端到端：在真实 CPA 里加载插件，接一个模拟的 Codex 上游跑一遍
make build   # 编译 dist/codex-reorder.so
```

`make smoke` 需要 CPA 的可执行文件，没有的话会从 `CPA_SRC`（默认 `../CLIProxyAPI`）编译一个。它会检查：新对话平铺、紧迫的号先用、老对话不换号、遇到 429 或 502 换号且不换回、CPA 重启后绑定还在、面板预览和保存、带前缀的模型、自动开窗、额度查询、API Key 交还给 CPA 等。想留着环境手动看面板：

```bash
go run ./test/smoke -keep
```

冒烟测试里的模拟账号其实是配置文件里的 API Key（CPA 的授权文件没法指向模拟上游），所以冒烟配置开着 `manage_api_keys`。

### 代码结构

```
abi.go                  C ABI 导出与宿主回调（cgo）
plugin.go               插件入口：方法分发、配置、管理接口、面板、日志
probe.go                额度查询的两个管理接口
warmup.go               开窗后台任务和“立即开窗”接口
lineage.go              从 CPA 元数据和请求头读取对话来源
internal/reorder/       调度引擎（纯 Go，不依赖 cgo）
  engine.go             对话绑定、选号、用量处理
  rank.go               新对话排序和原因
  image.go              生图请求的分配和生图额度
  config.go             配置解析
  events.go             日志事件和统计
  quota.go              额度响应头和查询结果解析
  probe.go              查询结果写入账号状态
  warmup.go             开窗计划
  warmup_config.go      开窗配置解析
  lineage.go            对话来源记录
  snapshot.go           面板数据
  persist.go            状态文件
web/dashboard.html      面板页面（编译时嵌入）
test/smoke/             端到端冒烟测试
```
